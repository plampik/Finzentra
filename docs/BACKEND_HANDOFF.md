# Finzentra — состояние frontend и передача backend-разработчику

**Назначение документа:** описать текущие возможности frontend, его модели
данных и правила работы, а также вопросы, которые нужно решить для интеграции
backend. Реализованные функции отделены от предложений по API.

## 1. О проекте

Finzentra — адаптивный русскоязычный личный кабинет для учета финансов
индивидуального предпринимателя или компании. Проект построен на React 19,
TypeScript, Vite 8 и Tailwind CSS 4. В приложении есть четыре основных раздела:

- **Дашборд** — отчеты P&L и Cash Flow, фильтры по периоду и проектам,
  отображение сумм в рублях или процентах.
- **Операции** — создание, редактирование, удаление, поиск и фильтрация
  доходов, расходов и налогов, введенных вручную.
- **Проекты** — создание и переименование направлений деятельности,
  архивирование и восстановление, просмотр числа операций.
- **Настройки** — управление категориями доходов, расходов и налогов.

При входе открывается главный экран сервиса с переходами к регистрации и входу.
Экран регистрации и входа сейчас является только frontend-интерфейсом для
будущего подключения backend. Демо-кабинет можно открыть отдельно. Ни
регистрация, ни вход пока не создают учетную запись и не выполняют
аутентификацию.

## 2. Текущее состояние реализации

### Уже реализовано во frontend

- Адаптивные интерфейсы для компьютеров, планшетов и телефонов; мобильная
  нижняя навигация учитывает безопасные зоны устройств.
- Формы регистрации и входа с проверкой обязательных полей, формата email,
  минимальной длины пароля и совпадения паролей на стороне браузера.
- Интерфейс CRUD операций и клиентская валидация.
- Создание, переименование, архивирование и восстановление проектов; защита
  от потери истории операций.
- Создание, скрытие/показ и контролируемое удаление категорий.
- Поиск операций по комментарию, сумме, датам, проекту и категории.
- Фильтрация истории операций по типу, проекту и дате факта: за всё время,
  месяц, квартал или год. Сначала показываются операции с более поздней датой
  факта.
- Фильтры дашборда по проектам и периоду, переключение P&L / Cash Flow,
  отображения в рублях / процентах, сравнение выбранного периода с другим,
  разбивка по категориям, итоговые суммы и состояние без данных.
- Локальное хранение данных в браузере и проверка их структуры при загрузке.
- PWA-манифест, иконки и service worker для кэширования оболочки приложения и
  статических ресурсов в production. Финансовые записи service worker не
  кэширует.

### Пока не реализовано — требуется backend

- Регистрация пользователей, вход, выход, восстановление пароля, сессии или
  токены, роли, организации/тенанты и разграничение доступа.
- HTTP-клиент, сетевые запросы, серверное хранение данных, синхронизация и
  доступ к одним данным с разных устройств.
- Серверные отчеты, пагинация, обработка конфликтов, аудит изменений и
  отображение серверных ошибок.
- Реальное сохранение типа аккаунта. Переключатель `ИП` / `Компания` сейчас
  меняет только состояние интерфейса.
- Серверные состояния загрузки и ошибок. Кабинет работает в демо-режиме, а
  источником данных служит `localStorage`.

Пароли не сохраняются в `localStorage` и никуда не отправляются. Переход в
демо-кабинет не является аутентификацией и не должен считаться защищенным
маршрутом.

## 3. Текущие модели данных

Ниже приведены фактические модели TypeScript из
[`src/types.ts`](../src/types.ts). Названия полей соответствуют используемым
клиентом JSON-полям.

### Проект

```ts
{
  id: string,
  name: string,            // обязательное поле, максимум 100 символов в UI
  description?: string,
  is_active: boolean       // false означает, что проект в архиве
}
```

В интерфейсе проект нельзя удалить физически. Архивирование исключает его из
фильтров активных проектов и выбора при создании операции, но уже существующие
операции и отчеты должны сохранять связь с ним.

### Категория

```ts
{
  id: string,
  name: string,
  type: "INCOME" | "EXPENSE" | "TAX",
  is_system: boolean,
  is_active: boolean       // false означает, что категория скрыта/неактивна
}
```

Интерфейс запрещает повторяющиеся названия в рамках одного типа категории
(сравнение без учета регистра), позволяет скрывать системные категории, но не
удалять их. Пользовательскую категорию, на которую ссылается операция,
удалить нельзя. Неактивные категории не включаются в отчеты и недоступны при
создании операции; исторические операции продолжают ссылаться на свои
категории.

Текущие системные категории:

- Доходы: `Доход от ВБ`, `Продажа книг`, `Услуги`.
- Расходы: `Аренда`, `Зарплата`, `Коммуналка`, `Интернет`, `Расходники`,
  `Прочие`.
- Налоги: `УСН 6%`, `УСН 15%`, `Страховые взносы`, `НДФЛ`,
  `Транспортный налог`.

Список категорий и постоянные идентификаторы записей должны управляться
backend. Не следует использовать demo-ID из frontend как идентификаторы
производственной базы данных.

### Операция

```ts
{
  id: string,
  project_id: string,
  category_id: string,
  type: "INCOME" | "EXPENSE" | "TAX",
  amount: number,          // положительная сумма в рублях, до 2 знаков
  date_fact: string,       // YYYY-MM-DD; дата фактического движения денег
  date_period: string,     // YYYY-MM-DD; дата отнесения к отчетному периоду
  comment?: string,        // максимум 255 символов
  created_at: string       // дата и время в формате ISO
}
```

`date_fact` и `date_period` разделены намеренно. При создании операции обе даты
по умолчанию равны сегодняшней; изменение `date_fact` обновляет `date_period`,
пока пользователь не изменит последнюю вручную. Для всех типов операций сумма
положительная; поле `type` определяет, к доходам, расходам или налогам
относится запись. Налоги вводятся вручную, frontend их не рассчитывает.

**Рекомендация по интеграции:** используйте на стороне API и базы данных
представление, безопасное для десятичных вычислений (например, сумму в копейках
целым числом или десятичную строку). До замены текущего `number` в рублях
согласуйте единицу измерения ответа. Нельзя незаметно смешивать рубли и копейки.

## 4. Существующие бизнес-правила

### Дашборд и отчеты

- По умолчанию дашборд показывает текущий месяц и P&L.
- Доступны периоды месяц, квартал и год; список лет включает предыдущий,
  текущий и следующий годы, а также годы, обнаруженные в датах операций.
  Режима «за всё время» на дашборде нет.
- Сравнение периодов выключено по умолчанию. При включении начальным периодом
  сравнения становится предыдущий период того же типа; его можно изменить.
  Сравнение использует тот же набор проектов и метод учета, что и основной
  отчет, а карточки показывают процентное изменение относительно выбранного
  периода сравнения.
- По умолчанию выбраны все активные проекты. Архивные проекты нельзя выбрать
  в этом фильтре.
- **P&L** отбирает операции по `date_period`.
- **Cash Flow** отбирает операции по `date_fact`.
- В оба отчета включаются только операции выбранных проектов с активной
  категорией.
- Итоги группируются по доходам, расходам и налогам; чистая прибыль считается
  как `доходы - расходы - налоги`.
- Разбивка строится по активным категориям и сортируется по убыванию суммы;
  категории с нулевой суммой не показываются.
- При отображении в процентах знаменателем служит общий доход. Поведение
  форматтера при нулевом доходе нужно сверить и зафиксировать в ходе интеграции.
- Сейчас frontend рассчитывает отчет по полному массиву операций. Для больших
  объемов данных нужно решить, переносить ли фильтрацию и агрегацию на сервер
  и в каком формате возвращать итоги и разбивку.

### Операции

- Для новой операции по умолчанию выбран тип `EXPENSE`, первый активный проект
  и первая активная категория выбранного типа.
- Сумма должна быть больше нуля и содержать не более двух знаков после запятой.
- Комментарий обрезается по краям и ограничен 255 символами.
- Список категорий зависит от типа операции и содержит только активные
  категории.
- История операций фильтруется по дате факта, даже если дата P&L отличается.
- Перед удалением интерфейс просит подтверждение.

### Проекты и категории

- Название проекта ограничено 100 символами. Проекты архивируются и
  восстанавливаются, но не удаляются.
- Созданный проект автоматически добавляется в текущий фильтр проектов.
- Тип категории: `INCOME`, `EXPENSE` или `TAX`.
- Системные категории нельзя удалить. Пользовательскую категорию, на которую
  ссылаются операции, также удалить нельзя — предлагается скрыть ее.

## 5. Демоданные и локальное хранилище

Сейчас приложение инициализируется данными `INITIAL_PROJECTS`,
`INITIAL_CATEGORIES` и `INITIAL_TRANSACTIONS` из
[`src/types.ts`](../src/types.ts). Это демоданные и данные для приемочных
сценариев, в том числе примеры за октябрь–ноябрь 2026 года; они не являются
источником достоверных пользовательских данных. Не добавляйте их в
производственные учетные записи без отдельного решения.

Проекты, категории и операции сохраняются отдельно в `localStorage` браузера:

- `finzentra_v2_projects`
- `finzentra_v2_categories`
- `finzentra_v2_transactions`

Хранилище проверяет загруженные данные и сообщает об ошибке поврежденного или
недоступного `localStorage`. Эти ключи — внутренняя деталь frontend, а не
контракт API. При переходе на серверное хранение нужно определить, отключаются
ли демоданные, переносятся или импортируются.

## 6. Предлагаемый контракт API

Этот раздел — отправная точка для обсуждения; перечисленные эндпоинты в
кодовой базе не реализованы. Рекомендуется версионированный JSON API. Контекст
пользователя и организации следует получать из аутентифицированной сессии, а
не доверять переданному клиентом `owner_id`.

### Аутентификация

- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `POST /api/v1/auth/password/forgot`
- `POST /api/v1/auth/password/reset`
- `GET /api/v1/me`

До подключения формы согласуйте способ работы сессии (для браузерной сессии
рекомендуется защищенная cookie `HttpOnly`, либо отдельно выбранная схема
токенов), защиту от CSRF, подтверждение email, требования к паролю,
представление типа аккаунта и связи пользователя с организацией.

### Рабочие данные

- `GET/POST /api/v1/projects`; `PATCH /api/v1/projects/{id}` для
  переименования и архивирования/восстановления.
- `GET/POST /api/v1/categories`; `PATCH /api/v1/categories/{id}` для
  переключения активности. Удаление — только если это допускают правила
  ссылочной целостности на сервере.
- `GET/POST /api/v1/transactions`; `PATCH /api/v1/transactions/{id}`;
  `DELETE /api/v1/transactions/{id}`.
- `GET /api/v1/reports/summary` — опционально, если отчеты рассчитывает
  сервер; запрос должен принимать период, идентификаторы проектов и метод
  учета.

Возможные параметры запроса для истории: `type`, повторяемый `project_id`,
`period_kind`, `year`, `month` или `quarter`, `date_from`, `date_to`, `search`,
`page`, `page_size`, `sort`. Нужно выбрать, будет ли режим «за всё время»
задаваться отдельным типом периода или отсутствием границ дат.

### Рекомендации по интеграции

- Идентификаторы и временные метки должны приходить с сервера; клиенту не
  следует создавать авторитетные ID через `Date.now()`.
- Все проверки данных и прав доступа/принадлежности к организации нужно
  выполнять на сервере независимо от браузерной валидации.
- Для отображения истории возвращайте необходимые данные проекта и категории
  либо предоставляйте стабильные справочники, с которыми клиент сможет
  связать записи.
- Определите поведение при параллельном изменении или удалении (например,
  `409 Conflict` с понятным сообщением или проверка версии/ETag).
- Используйте единый формат ошибок, например:
  `{ "code": "VALIDATION_ERROR", "message": "...", "fields": { ... } }`.
- Зафиксируйте единицы и точность сумм, семантику часового пояса для дат без
  времени, настройки пагинации и сортировки, видимость архивных проектов и
  обработку неактивных категорий.
- Решите, являются ли итоги отчетов авторитетным результатом сервера или
  рассчитываются на клиенте по полному набору данных. Для серверного расчета
  задайте формат итогов, чистой прибыли и разбивки по категориям.

## 7. Где подключать backend во frontend

- [`src/App.tsx`](../src/App.tsx): навигация кабинета, вход/выход из демо,
  координация интерфейсов проектов и категорий.
- [`src/components/AuthScreen.tsx`](../src/components/AuthScreen.tsx):
  интерфейс регистрации и входа; пока нет auth-сервиса или callback для
  отправки формы.
- [`src/components/Transactions.tsx`](../src/components/Transactions.tsx):
  форма операции, клиентская валидация, фильтры и поиск истории, CRUD-callback.
- [`src/components/Dashboard.tsx`](../src/components/Dashboard.tsx): фильтры
  отчета и его отображение.
- [`src/components/UiControls.tsx`](../src/components/UiControls.tsx): общие
  контролы периода, сегментные переключатели и фильтр проектов.
- [`src/store.ts`](../src/store.ts): локальный источник данных и CRUD. Это
  основная точка для замены/выделения API-репозитория.
- [`src/report.ts`](../src/report.ts): текущая клиентская логика расчетов.
- [`src/period.ts`](../src/period.ts): модель периодов и фильтрация по датам.
- [`src/format.ts`](../src/format.ts): форматирование валюты, процентов и дат.

Сейчас callback компонентов синхронные. Для API понадобятся асинхронные
callback-типы, состояния загрузки, успеха и ошибки. Нельзя показывать локальный
или демо-результат как подтверждение успешного изменения на сервере.

## 8. Что согласовать до начала реализации

1. Учетная запись соответствует одному пользователю или организации? Может ли
   пользователь состоять в нескольких организациях? Какие роли нужны:
   владелец, администратор, участник?
2. Какие поля профиля и значения типа аккаунта обязательны при регистрации?
   Нужно ли подтверждать email?
3. Как устроены сессия, ее срок действия, выход и восстановление пароля?
4. Являются ли `ИП` и `Компания` разными юридическими типами? Какие реквизиты
   (например, ИНН) собираются и проверяются?
5. Рубли — единственная валюта? Каковы базовая единица хранения суммы и
   правила округления?
6. Даты — календарные даты или моменты времени в конкретном часовом поясе?
   Сейчас интерфейс использует даты без времени в формате `YYYY-MM-DD`.
7. Где рассчитываются отчеты? Какие параметры запроса и точный формат ответа
   должен использовать frontend?
8. Исключаются ли скрытые категории из исторических отчетов? Сейчас frontend
   исключает операции с неактивными категориями из отчетов.
9. Должны ли архивные проекты присутствовать в фильтрах истории? Сейчас выбор
   ограничен активными проектами, но исторические операции сохраняют связь с
   архивированным проектом.
10. Нужно ли удалить демо- и приемочные данные, оставить их в отдельном демо-
    тенанте или предлагать явную загрузку примера?
11. Каковы лимиты и правила пагинации, смысл поиска, порядок сортировки,
    формат ошибок валидации и поведение при параллельном изменении данных?

## 9. Рекомендуемая последовательность интеграции

1. Согласовать контракты аутентификации, учетной записи/организации,
   идентификаторов, дат и сумм.
2. Реализовать миграции/начальные данные и API для проектов, категорий и
   операций; добавить серверные проверки прав и данных.
3. Добавить типизированный API-клиент и заменить операции чтения/изменения в
   локальном store асинхронными запросами, сохранив текущие бизнес-правила.
4. Добавить состояния загрузки, ошибок и пустого результата; отображать ошибки
   серверной валидации в существующих формах. Не хранить учетные данные или
   токены доступа в `localStorage`.
5. Решить, где считаются отчеты, и проверить приемочный сценарий с различными
   датами P&L и Cash Flow.
6. Определить судьбу локальных демоданных; проверить работу нескольких
   пользователей и границы доступа.
7. Проверить полный сценарий на компьютере и телефоне, включая истечение
   сессии, сетевые ошибки и поведение без интернета.

## 10. Запуск и проверка frontend

```bash
npm install

npm run build
```

На момент передачи в проекте не настроены переменные окружения backend и
API-клиент.

## 11. Примеры обмена данными для согласования

Ниже приведены **рекомендуемые примеры**, а не существующий контракт. Их нужно
согласовать между frontend- и backend-разработчиками до начала подключения.
Во всех примерах предполагается, что пользователя и организацию сервер
определяет из аутентифицированной сессии, а не из переданного клиентом
`owner_id`.

### Создание операции

Пример запроса `POST /api/v1/transactions`:

```json
{
  "project_id": "project-id",
  "category_id": "category-id",
  "type": "EXPENSE",
  "amount": "1250.50",
  "date_fact": "2026-10-28",
  "date_period": "2026-10-28",
  "comment": "Оплата аренды"
}
```

Предпочтительно передавать денежную сумму десятичной строкой, чтобы избежать
неявной потери точности в JSON-числе. Если API выберет целое число копеек,
это необходимо явно зафиксировать и преобразовывать на frontend в одном
типизированном адаптере.

Пример ответа `201 Created`:

```json
{
  "id": "transaction-id",
  "project_id": "project-id",
  "category_id": "category-id",
  "type": "EXPENSE",
  "amount": "1250.50",
  "date_fact": "2026-10-28",
  "date_period": "2026-10-28",
  "comment": "Оплата аренды",
  "created_at": "2026-10-28T10:00:00Z",
  "updated_at": "2026-10-28T10:00:00Z"
}
```

Идентификаторы и серверные временные метки в ответе — пример рекомендуемого
поведения; сейчас frontend создаёт временные ID и `created_at` сам. Сервер
должен проверить принадлежность проекта и категории текущей организации,
совпадение типа операции и категории, активность справочников и ограничения
суммы/дат/комментария.

### Фильтры журнала операций

Предлагаемый пример запроса:

```text
GET /api/v1/transactions?type=EXPENSE&project_id=project-id&page=1&page_size=25&sort=-date_fact
```

Для нескольких проектов можно использовать повторяемый параметр
`project_id=...&project_id=...` либо согласовать иной формат. Определите
единый способ передавать период, поиск и признак «за всё время». История
сейчас сортируется по `date_fact` от новых к старым; поиск выполняется по
комментарию, сумме, датам, проекту и категории.

Рекомендуемая обёртка ответа для пагинации:

```json
{
  "items": [],
  "page": 1,
  "page_size": 25,
  "total": 0
}
```

Пагинация не реализована в текущем UI; размер страницы, управление страницами
и серверную фильтрацию необходимо добавить согласованно.

### Параметры сводного отчёта

Пример запроса:

```text
GET /api/v1/reports/summary?period_kind=MONTH&year=2026&month=10&method=PNL&project_id=project-id
```

Минимальная форма ответа, если расчёты выполняются на сервере:

```json
{
  "period": {
    "kind": "MONTH",
    "year": 2026,
    "month": 10
  },
  "method": "PNL",
  "totals": {
    "income": "15000.00",
    "expense": "10000.00",
    "tax": "0.00",
    "net": "5000.00",
    "transaction_count": 3
  },
  "categories": [
    {
      "id": "category-id",
      "name": "Услуги",
      "type": "INCOME",
      "amount": "15000.00"
    }
  ]
}
```

P&L использует `date_period`, Cash Flow — `date_fact`. Итог должен учитывать
только выбранные проекты и активные категории; чистый результат равен
`income - expense - tax`. Если сравнение выполняется на сервере, согласуйте
отдельно параметры и структуру второго периода и его итогов. Отображение
рублей/процентов может оставаться клиентским, если сервер возвращает точные
суммы и валюту.

### Ошибки API и состояния UI

Рекомендуемый пример ошибки валидации (`422 Unprocessable Entity`):

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Проверьте введённые данные.",
  "fields": {
    "amount": "Сумма должна быть больше нуля."
  }
}
```

До реализации согласуйте статусы для отсутствующей сессии (`401`), запрета
действия (`403`), отсутствующей записи (`404`) и конфликта конкурентного
изменения (`409`). Клиент должен различать загрузку, успешный ответ и ошибку;
ошибка сети не должна выглядеть как сохранённая операция.

## 12. Интеграционный чек-лист

- [ ] Согласовать пользователя, организацию, роли, сессию и способ CSRF-защиты.
- [ ] Зафиксировать схему API, денежные единицы, точность, формат дат и ошибок.
- [ ] Реализовать серверные ограничения и проверки принадлежности всех
  идентификаторов организации.
- [ ] Добавить отдельные типизированные API-модели/адаптеры, не смешивать
  сетевые DTO напрямую с формами и бизнес-логикой интерфейса.
- [ ] Заменить `useFinanceStore` асинхронным источником данных; определить
  начальную загрузку, повтор запроса, отмену устаревших запросов и обработку
  конфликтов.
- [ ] Убрать создание авторитетных ID на клиенте после включения API.
- [ ] Согласовать переход с `localStorage`: демо-режим, миграция, экспорт или
  сброс локальных данных. Не отправлять автоматически локальные демоданные в
  рабочую организацию.
- [ ] Добавить серверную пагинацию, если объём операций этого требует.
- [ ] Решить, где рассчитываются отчёты, и сверить P&L/Cash Flow на операциях с
  разными `date_fact` и `date_period`.
- [ ] Проверить сценарии прав доступа, сетевых ошибок, истечения сессии,
  мобильного интерфейса и нескольких организаций.
